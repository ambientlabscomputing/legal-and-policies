# Policy readiness review

Reviewed September 27, 2026. Status: **not ready to use unchanged for app submissions**.

Scope: all four files in `src/content`, plus the resolver, renderer, README usage examples,
and existing tests. No consuming app, SDK configuration, backend, published URL, or store
console was audited. The intended consumers are SiteRF, Jog Actuators, and Tilly; the owner
confirmed that accounts, subscriptions, SDKs, AI, and permissions may apply depending on the
app. Their exact feature mapping remains unverified. This is a technical policy-readiness review, not a legal
opinion or assurance of store approval.

The existing titles, company/product variables, contact email, effective date, and section
anchors provide a useful foundation. The missing work is accurate product-specific content
and evidence that the app implements the stated practices.

## Findings to resolve before submission

### 1. High: data collection and recipient disclosures are too generic

Location: `src/content/privacy-policy.ts`, lines 18–46.

“Information generated by your use” and “privacy-conscious analytics” do not identify the
actual data involved. The template assumes account information and analytics without a
product inventory. The no-sale statement and narrow sharing exceptions are unverified.

For each app, document actual categories, sources, purposes, recipients, and user controls.
Check account identifiers, IP addresses, diagnostics, uploaded files/photos, purchases,
device identifiers, permission-protected data, and AI inputs/outputs where applicable.
Distinguish data kept on-device from transmitted data. Identify relevant providers and
their roles; do not add categories or vendors the product does not use.

Apple requires explicit collection/use disclosures and equivalent protections by data
recipients; confidentiality alone does not establish that protection. Verify contracts and
practices before strengthening the promise. [Apple §5.1.1](https://developer.apple.com/app-store/review/guidelines/#privacy)

### 2. High, if accounts exist: deletion is reduced to an email request

Location: `src/content/privacy-policy.ts`, lines 49–60.

Add a prominent account-deletion section explaining the actual in-app entry point, external
request route, verification, completion timing, affected data, retained exceptions, and
subscription consequences. An email privacy contact can remain for other rights requests.

Apple requires in-app initiation and ordinarily disallows mandatory email/support flows.
Deletion must remove the account and associated data, subject to legal retention; disabling
an account is insufficient. Revoke Sign in with Apple tokens when applicable.
[Apple account deletion](https://developer.apple.com/support/offering-account-deletion-in-your-app/)

Google requires both an in-app route and an external web resource for covered account-creating
apps. The resource must identify the app/developer and provide an actionable deletion request
path. A prominently anchored privacy-policy section can qualify; a separate page is not
inherently mandatory. [Google deletion requirements](https://support.google.com/googleplay/android-developer/answer/13327111?hl=en)

No deletion implementation is present in this library, so its existence remains unverified.

### 3. High: no security disclosure and insufficient retention detail

Location: `src/content/privacy-policy.ts`, lines 49–53 and the overall section list.

Google explicitly requires secure-handling, retention, and deletion disclosures.
[Google User Data policy](https://support.google.com/googleplay/android-developer/answer/10144311?hl=en)

Describe verified safeguards such as transport security and access restrictions, without
claiming certifications or absolute security. Replace the open-ended retention paragraph
with meaningful periods or criteria by category, including inactive accounts, support
records, logs, backups, and lawful exceptions after deletion. Establish operational timings
before promising them; there is no universal store-mandated “30 days” to insert.

### 4. High: the introduction treats usage as consent to all collection

Location: `src/content/privacy-policy.ts`, lines 13–15.

The final “By using” consent sentence was removed during this review. The introduction now
remains a neutral notice of what the policy explains. Still add accurate instructions for withdrawing optional consent.
Neither accepting terms nor publishing this notice supplies every required permission.

Apple requires permission controls and specifically calls for explicit permission before
sharing personal data with third-party AI. Google's prominent-disclosure rules can require
an affirmative in-app flow before unexpected sensitive-data collection.
[Apple §5.1](https://developer.apple.com/app-store/review/guidelines/#privacy),
[Google User Data policy](https://support.google.com/googleplay/android-developer/answer/10144311?hl=en)

### 5. High: unresolved variables can reach published pages

Location: `src/render/interpolate.ts`, lines 6–9;
`src/content/terms-of-service.ts`, line 60; README usage examples.

Unknown variables intentionally remain unchanged. Reusing the README variables for the
terms leaves `{{jurisdiction}}` visible. Existing resolver coverage exercises privacy, not
every template with each consumer's production configuration.

Add a release-time validation step for all resolved titles and bodies that rejects remaining
template tokens, empty identity/contact values, invalid dates, and duplicate section IDs.
Supply the actual jurisdiction rather than choosing one from a developer's location.
Preserve permissive preview behavior only if production validation is mandatory.

### 6. Conditional: subscription terms and the Apple license choice are missing

Location: `src/content/terms-of-service.ts`, overall section list.

For paid plans, add verified billing, trial conversion, renewal, cancellation, refund, and
post-cancellation access terms, distinguishing each billing channel. Paywall disclosures
must also match the offer; Google requires clear subscription terms and an accessible online
cancellation method. [Google subscriptions](https://support.google.com/googleplay/android-developer/answer/9900533?hl=en)

Decide whether the app uses Apple's standard EULA or a custom EULA. The standard agreement
applies absent a custom one; this short service-terms template should not be assumed to meet
custom EULA minimums. [Apple license setup](https://developer.apple.com/help/app-store-connect/manage-app-information/provide-a-custom-license-agreement)

Additional product-contract gaps, distinct from universal store requirements: user-content
ownership and limited processing license; eligibility; termination and export consequences;
non-waivable consumer rights; and product-specific limitations, such as field verification
for measurement tools. Confirm these with the business and legal reviewer before drafting.

### 7. Conditional: cookie practices and audience assumptions are unverified

Locations: `src/content/cookie-policy.ts`, lines 16–27;
`src/content/shared/legal-terms.ts`, lines 3–6.

The cookie template positively claims authentication, preference, and analytics cookies.
Inventory actual cookies and similar storage: name/provider, purpose, duration, and category.
Document the real preference/rejection/withdrawal controls. Browser settings alone do not
establish valid consent where required. Assess applicable exceptions rather than assuming
all analytics are exempt or all storage needs consent.
[ICO storage/access guidance](https://ico.org.uk/for-organisations/direct-marketing-and-privacy-and-electronic-communications/guidance-on-the-use-of-storage-and-access-technologies/what-are-storage-and-access-technologies/)

The under-13 clause is an audience claim, not an age gate or universal age-of-consent rule.
Confirm target ages, actual access controls, and store audience declarations. Child-directed
apps need a separate assessment. Likewise, confirm launch territories: where GDPR applies,
Articles 13–14 address controller details, legal bases, recipients, transfers, retention,
rights, complaints, and other notices as applicable. The current generic rights paragraph
does not cover that assessment. [GDPR](https://eur-lex.europa.eu/legal-content/EN/TXT/?uri=CELEX%3A32016R0679)

## Product facts needed to finalize copy

Complete one record each for SiteRF, Jog Actuators, and Tilly; shared templates do not imply
shared data practices. Launch countries and intended minimum ages are still undecided or
not supplied for this review.

| Topic | Required decision or evidence |
| --- | --- |
| Identity | App/store name, contracting entity, privacy contact, applicable business address |
| Audience | Launch countries, intended ages, organization-managed versus personal accounts |
| Data | Category → source → purpose → on-device/server → recipient → retention → controls |
| Vendors | Auth, hosting, payments, analytics, crash reporting, support, advertising, AI; actual configuration |
| Permissions | Requested permission, feature, accessed data, transmission, denial/revocation behavior |
| Deletion | In-app path, public request URL, processor cleanup, backup handling, exceptions and timings |
| Commercial | Billing channels, trials, renewals, cancellation/refunds, Apple EULA choice |
| Web storage | Cookie/local-storage inventory and consent/preference behavior |

Use `sectionOverrides` for app-specific facts and `customSections` for applicable features.
Keep operational commitments out of shared defaults unless every consumer satisfies them.

For the next library revision, introduce explicit per-app profiles with required disclosure
fields and feature-specific sections. A feature being disabled should omit its clauses;
an enabled feature should require its actual disclosure text. The current resolver cannot
omit a standard section, so overriding its body with an empty string is not an adequate
substitute. Keep stable IDs when expanding sections so consumer overrides continue to work.
Add production validation and tests for enabled/disabled features, missing facts, and
unresolved tokens before migrating the three consumers. Do not default unknown practices
to “no collection,” “no tracking,” or a guessed retention period.

- [ ] Exercise deletion end-to-end, including the published web route and retained-data notices.
- [ ] Verify required permission/consent flows before collection, including AI sharing if applicable.
- [ ] Verify applicable subscription, child-audience, tracking, and user-generated-content flows.
- [ ] Check privacy and terms links on paywalls and account/settings screens. The current
  `PolicySection` renders plain text: Markdown/HTML URLs inserted into `body` will not become
  clickable links. Implement links in the consuming UI or extend rendering safely.
- [ ] Supply working reviewer access and backend services; validate support URLs and metadata.
  [Apple submission checklist](https://developer.apple.com/app-store/review/guidelines/#before-you-submit)

Completion means matching text, app behavior, backend practices, vendor configuration, and
store declarations. This repository alone cannot verify the latter four.
